# Rust V2 真实媒体 CPU / 磁盘 I/O 调度诊断

## 结论

本轮 30 分钟真实媒体只读跑测已完成，证据门禁为 `PASS`。用户观察到的“磁盘高时 CPU 低、空闲 Worker 多；磁盘低时 CPU 高、空闲 Worker 少”成立，而且在三轮扫描中重复。它不是少数 Worker 长期抢占任务，而是计算流水线的供给与消费阶段出现周期性填充/排空：

1. **Worker 槽位之间分配均衡。** 12 个槽位累计 CPU 占比均在 `8.20%～8.55%`，有效槽位数约 `12.00`；没有持续由少数 Worker 吃掉大部分 CPU 的证据。
2. **生产阶段存在明确的 CPU / I/O 反向相位。** I: 读取 `>=300 MiB/s` 时，Worker 平均仅使用 `7.62` 核、空闲 `4.12` 个；读取 `(0,100) MiB/s` 时，Worker 平均使用 `11.51` 核、空闲仅 `0.29` 个。高吞吐段的 Worker CPU 比低速段低 `33.79%`。仅在 I: 非零读取样本中，吞吐与 Worker CPU 的时间加权相关系数为 `-0.570`，与空闲 Worker 为 `+0.528`。
3. **当前架构会放大这种交替。** Hash 全文件读取与 Worker 媒体解码共享 16 个磁盘许可，但公平性按“许可次数”而不是字节、占用时长或 Worker 饥饿程度调节；媒体许可等待又计入 12 个 Worker admission 上限。高 I/O 段平均约 `9.11` 个 Hash 许可加 `5.89` 个媒体许可，接近占满 `15 / 16`，同时只有 `7.88` 个 Worker 真正在工作。这是跨文件流水线的批量填充/排空，不是全局“先读完全部文件再统一计算”。
4. **CPU 的逻辑核利用不均衡。** 全机平均约使用 `9.97 / 24` 个核当量，Worker 平均 `7.26` 个核当量；逐核平均负载最高 `72.49%`、最低 `2.90%`，变异系数 `0.612`。这说明 Windows 最终把线程调度到逻辑核时存在热点，但当前证据不能把热点直接归因给某个 Worker、某个线程或 Node 调度器。
5. **另有可重复的约 120 秒终态发布尾段。** 前两次完整扫描在文件计数已经闭合、全部队列和资源计数归零后，任务仍保持 `running` 约 `120.9` 秒；两段合计 `241.781` 秒，占 30 分钟窗口的 `13.43%`。该尾段与上述生产阶段交替波形是两个独立问题，不能混在相关性分析中。

因此，当前优先级应是：**先拆分媒体许可等待与实际 Worker 工作状态，再给媒体读取保留最低服务能力并抑制 Hash 突发；终态收尾并行排查；最后才评估增加 Worker。** 直接增加 Worker 或把 I: 的读取许可继续调高，没有本轮数据支持，反而可能加深磁盘排队和相位振荡。

零读取组包含启动、两次约 120 秒终态尾段以及任务切换，不适合与生产阶段做单调相关。初始 `16.136` 秒尚无流水线 current 指标，表中按 0 计入，且只影响零读取组。只看 I: 非零读取样本，I: 吞吐与 Worker CPU、活动 Worker、空闲 Worker 的时间加权 Pearson 相关系数分别为 `-0.570`、`-0.528`、`+0.528`。若把终态尾段混入全窗口，吞吐与 Worker CPU 会被扭曲成弱正相关 `+0.138`。

该关系不是某一轮偶然值：三轮扫描中，从低速非零段切换到 `>=300 MiB/s` 高速段时，Worker CPU 分别下降 `36.05%`、`33.17%` 和 `34.00%`。用“高吞吐、Worker CPU 小于 9 核、至少 3 个 Worker 空闲”定义的可见波段共有 32 段、累计 `351.57` 秒，最长 `53.03` 秒；相反的“低速读取、Worker CPU 至少 10 核、至多 1 个 Worker 空闲”共有 52 段、累计 `494.36` 秒，最长 `53.26` 秒。

### 架构解释

当前实现不是全局“先完成全部读取，再完成全部计算”，而是跨文件重叠、单文件串联：

`全文件 MD5 Hash → 缓存判断 → Worker 探测/解码 → 关闭媒体源并释放媒体许可 → CPU 特征计算 → 持久化`

交替波形由有界流水线的填充/排空放大：

1. **Hash 供给波。** 高 I/O 段 `hash_io + media_io` 平均为 `14.99 / 16`，其中 Hash 独占约 `9.11` 个许可。媒体许可的等待项会占用 Worker admission，但尚未下发给 Worker，结果是平均只有 `7.88` 个 Worker 活动、`4.12` 个空闲；磁盘队列高，CPU 消费端不足。
2. **Worker 消费波。** 低速非零段 Hash 实际 I/O 降至 `0.49`，约 `11.71` 个 Worker 活动，其中平均 `4.70` 个处于已关闭媒体源的纯 CPU 特征阶段；此时 CPU 高、磁盘队列接近零。`hash_queue=16` 只表示 JoinSet 中等待、读取或已完成但尚未消费的 future 数量，不等于 16 个实际磁盘读取。
3. **公平性只控制许可发放顺序。** 当前媒体与 Hash 的 `3:1` 权重只有在二者同时可发放时生效，已经持有的长时许可不会被抢占，也没有为“存在媒体等待且 Worker 空闲”保留最低媒体容量；按任务次数加权也不能反映完整文件 Hash 与少量视频帧解码的字节量和服务时间差异。
4. **有界队列形成批次同步。** 下游空间不足时，已经完成的 Hash future 可能仍留在 JoinSet 中；空间恢复后又集中补位。固定上限保证内存安全，却会把连续流量整形成约几十秒的供给波和消费波。

因此，现象主要是 **Node 的跨阶段许可、admission 与背压协同问题**，不是 WorkerPool 长时间不给某些 Worker 发下一条 `run`，也不能归结为 Windows 把单个 Worker 固定到了错误 CPU。单纯增加 Worker、读取线程或 16 个磁盘许可都不会修复供需波形。

## 任务尾部：可重复的 120 秒资源气泡

前两次完整任务都出现相同状态：基础计算项计数已经闭合，`worker_slots`、`cpu_weight`、Hash/媒体 I/O 许可及所有队列 current 全部归零，但任务仍为 `running`。

| 完整任务 | 首个资源全零且计数闭合 | 终态发布 | 尾段 |
| --- | ---: | ---: | ---: |
| 第 1 次 | elapsed 656 秒 | 约 776.889 秒 | 120.889 秒 |
| 第 2 次 | elapsed 1410 秒 | 约 1530.892 秒 | 120.892 秒 |
| 合计 | — | — | 241.781 秒，占全窗口 13.43% |

尾段内运行快照仍列出 12 个 Worker 槽，但它们全部为 `idle`，路径和物理盘字段均为空；`worker_slots.current=0` 也表示没有活动计算槽。除尾段首个系统样本外，后续 Worker CPU 和进程读计数均为 0。这里没有“旧路径仍挂在 Worker 上”的证据，真正滞后的是计算阶段/任务状态仍为 `running`。

同一阶段 Node 接近占用一个逻辑核，但物理盘读写和队列接近空闲，持久化队列历史峰值及延迟也不支持“普通 persist 队列积压”。直接证据只能确定：**Worker 已空闲、基础计算项计数已闭合，但计算阶段/任务终态约 120 秒后才发布。** 当前遥测没有把这段 Node 工作拆分出来，不能仅凭一核占用就断言其内部一定是单线程同步实现。

结合当前源码，首要假设仍是 `finalize_scan_task_from_items` 的逐文件存在性查询及缺少覆盖索引；它与两轮高度稳定的尾段长度吻合。但本轮没有 SQLite statement、锁等待、事务、WAL checkpoint 或 `EXPLAIN QUERY PLAN` 计时，因此报告不把该假设写成已经闭环的数据库因果结论。

## 调整优先级

### P0：先抑制生产阶段的供需振荡

1. 把现有聚合指标拆成 `hash_waiting_permit`、`hash_reading`、`hash_completed_unjoined`、`media_permit_waiting`、`media_permit_ready`、`worker_decode` 和 `worker_feature`；以 0.5～1 秒采样并记录每项阶段时间戳。
2. 当存在媒体许可等待且有空闲 Worker 时，暂停或限制新的 Hash 许可，给 `MediaDecode` 保留最低在途容量；具体保留值由相同媒体集 A/B 决定，不在缺少实验时硬编码。
3. Worker 高 CPU 阶段仍维持少量 Hash 后台供给，避免 `hash_io` 从接近 0 突然回填到 9 个以上许可；用低/高水位逐步补位，不按空位一次性灌满。
4. 公平调度从单纯 `3:1` 许可次数升级为同时考虑等待时间、估计字节量、磁盘队列和 Worker 饥饿信号；已持有许可保持不可抢占，但新许可必须服务于稳定流水线。
5. 验收同时比较每秒完成文件数、高 I/O 段空闲 Worker、吞吐与 Worker CPU 的相关性、磁盘队列 P95 和内存峰值。目标是降低相位振荡且不牺牲总吞吐，而不是让 CPU 或磁盘单项始终 100%。

### P0（并行）：消除或拆分 120 秒收尾

1. 在同一 task ID 下增加 `compute_resources_released`、`finalize_start/end`、SQLite statement/transaction/commit/checkpoint/lock wait 和 `terminal_published` 时间戳。
2. 对 `finalize_scan_task_from_items` 执行 `EXPLAIN QUERY PLAN`；优先把逐文件 `SELECT EXISTS` 改为一次反连接/批量失效，或增加覆盖 `task_id + machine_id + normalized_path` 的索引。
3. 给最终化建立规模回归：约 1.5 万文件时收尾不能随文件数接近平方增长，并将其独立显示为 `PersistFinalize`，不再伪装成 Worker 计算。
4. 运行详情必须单独上报 `PersistFinalize`/终态发布阶段，UI 和报告不能仅凭 `workers[]` 的槽位行数推断仍在计算。

### P1：用反馈式每盘并发代替固定 16 许可

1. 不依赖 SSD/HDD 识别，直接按每块物理盘的队列与延迟反馈调节许可。
2. 先在同一媒体集上做 `8 / 12 / 16` 三档 A/B，比较任务吞吐、P95 队列、零读时间和尾段，选择吞吐不降且队列更浅的档位。
3. Hash 与媒体读取继续共享同一物理盘预算；不要因为它们属于不同阶段而分别各自放满 16。
4. 共享不等于任一类别可以吃完预算：应与 P0 的媒体最低服务能力和 Hash 后台供给下限共同工作。
5. 在拿到有效读延迟前，以队列 P95/持续压力时间作为保守反馈；补齐 PDH/ETW 延迟后再采用目标延迟控制。

### P1：CPU 扩容必须在磁盘和收尾之后验证

1. 当前 12 Worker 对 Worker CPU 形成约 12 核的结构性上限，但读取期 I: 已经排队。先完成 P0 和每盘许可 A/B，再测试 `12 / 16` Worker，不能单独提高 Worker 数。
2. 门禁同时看每秒完成文件数、Worker 平均核当量、磁盘队列和错误率；若 CPU 上升但吞吐不升或队列继续加深，则回退。
3. 不先实施手工绑核。用 ETW 确认热点属于 Worker 用户态、Node、内核还是 I/O 中断，再决定 CPU Sets、亲和性或内部线程数。

### P2：降低系统采样器开销

当前采集平均耗时约 727 ms，并在固定 sleep 2 秒之外累加，导致实际周期约 2.74 秒。应改成按目标 deadline 调度，或用一次 PDH 查询批量采集进程、逐核和磁盘计数；采集器自身 CPU 与耗时需要单独上报。该修改提高观测精度，不应与生产吞吐提升混为同一项收益。

## 本轮裁决

- 真实媒体只读与 30 分钟运行证据：`PASS`。
- “少数 Worker/PID 长期集中导致 CPU 低”：**不成立**。
- “磁盘高时 CPU 低、空闲 Worker 多；磁盘低时 CPU 高、空闲 Worker 少”：**成立，三轮重复，是当前有界流水线的供给/消费相位振荡**。
- “逻辑核负载不均”：**成立，但尚未定位线程级原因**。
- “单源盘读取期排队过深，同时存在明显零读空窗”：**成立**。
- “Worker 空闲后的 Node 终态发布尾段显著拉低整体 CPU/I/O”：**成立，是与生产阶段振荡相互独立、需要并行优化的问题；内部同步/SQLite 因果待分段验证**。
- 本轮只完成测量、归因和报告，未修改生产部署目录。
