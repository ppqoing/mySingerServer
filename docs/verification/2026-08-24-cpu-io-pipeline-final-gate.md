## 新发现的任务尾部低利用率

前两次完整计算均出现可重复的空转收尾：

| 任务 ID | 全部队列与资源归零 | 任务完成采样 | 空转尾部 |
| --- | ---: | ---: | ---: |
| `e2d75078-1edf-4786-83da-0defa90d8a67` | 652 秒 | 773 秒 | 120.890 秒 |
| `195a3a43-cd9b-400d-829d-c9d0984ec3c5` | 1406 秒 | 1525 秒 | 118.875 秒 |

归零样本中 Hash、解码、持久化队列以及 Hash I/O、媒体 I/O、CPU 权重、Worker 槽均为 0，12 个 Worker 全部为 `idle`，但任务仍显示 `running / compute_base_features`。

高可信根因是 SQLite 收尾查询复杂度：

1. `BaseComputeEngine` 在全部流水线任务结束后同步调用 `finalize_scan_task_from_items`。
2. 该函数逐条遍历活动 `files`，并对每条文件执行一次按 `task_id + machine_id + normalized_path` 的 `SELECT EXISTS`。
3. 当前 `task_items` 只有 `(task_id, status, item_id)` 索引，不能完整覆盖上述路径查找；在约 1.48 万文件和同量任务项下形成接近二次复杂度的重复扫描。
4. 基础计算路径在该同步调用前没有启动 `PersistFinalize` 运行阶段，调用返回后才把 `ComputeBaseFeatures` 标为完成，因此 UI 把约 120 秒数据库收尾显示成“计算中且资源全空”。

这项判断由两轮相近尾部耗时、归零遥测和当前 SQL/索引结构共同支持；若要将其提升为数据库级最终定论，应在修复前后补充 `EXPLAIN QUERY PLAN` 和收尾阶段计时。

## 部署裁决与后续修改

本轮不打包替换生产目录。建议下一轮依次完成：

1. 将逐文件 `SELECT EXISTS` 改为单次反连接/批量失效，或增加能覆盖 `task_id, machine_id, normalized_path` 的索引，并补收尾规模回归。
2. 在基础计算路径显式上报 `PersistFinalize` 阶段及完成进度，避免把数据库收尾显示成 Worker 计算。
3. 重跑同机至少三轮 A/B；总墙钟中位数必须降低至少 15%。
4. 门禁通过后再成套打包 Node、Worker、Desktop 和协议库，保留旧包与 SHA-256 后替换生产目录。

除非用户明确决定接受不满足 15% 的结果，否则不能跳过第 3 步。
