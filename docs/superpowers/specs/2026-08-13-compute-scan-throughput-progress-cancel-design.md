# Compute 扫描吞吐、任务进度与停止设计

日期：2026-08-13  
状态：已确认，待实施  
目标运行目录：`D:\code\mySingerServer\publish\MySingerServer-Compute`

## 1. 文档目的

本设计解决 Compute 本地任务运行时的三个直接问题：

- 磁盘 0 与磁盘 2 不能持续并行工作，大部分 Worker 长时间处于空闲状态；
- NodeTray 创建本地任务后没有可见进度；
- 运行中的本地任务没有停止入口，且现有取消链路不能可靠停止扫描。

同时修复本次运行证据中暴露的图片处理、缩略图缓存目录和 SHA-512 错误持久化问题，避免调度优化完成后仍因生产处理链失败而没有有效产出。

本设计保持现有进程所有权不变：NodeTray 管理 Agent，Agent 管理 Worker；NodeTray 不直接启动、停止或强杀 Worker。

## 2. 当前证据与根因

### 2.1 全局字节限流造成跨磁盘互相阻塞

当前扫描路径使用全局加权信号量，并以文件大小作为权重。当文件大于配置容量时，其权重被压到信号量总容量，因此一个超大文件会占用全部额度。即使该文件只位于一块磁盘，其他磁盘的新文件也无法进入处理路径。

当前发布配置的 `pending_bytes_mb` 为 1024，而运行统计中单个磁盘的待处理字节可超过该值。该机制限制的是文件逻辑大小，不是实际内存占用；哈希和 VideoCore 文件会话本身采用流式读取，不需要为文件总大小预留等量内存。

### 2.2 Worker 空闲还受到图片生产路径失败影响

生产构建使用 VideoCore，但一筛图片仍被特殊分流到旧版 `mediacore` 路径。当前 Worker 构建不包含旧版 `legacy_mediacore` 标签，也不携带 `mediacore.dll`，导致图片处理返回 `cgo Windows binding unavailable`。

该前置错误发生后，结果尚无 SHA-512；存储层仍尝试编码空 SHA-512，又制造 `SHA-512 must be exactly 64 bytes, got 0` 的二次错误。二次错误会掩盖原始处理失败并让任务统计更难判断。

### 2.3 联系表缓存根目录没有在启动阶段建立

联系表缓存路径要求缓存根目录已经存在，而 Agent 启动阶段没有创建配置中的 `thumb.cache_dir`。因此运行中出现缓存根目录不存在错误。

### 2.4 本地任务没有形成进度闭环

Agent 协议已有任务进度消息，本地任务表也已有进度字段，但 Agent 本地任务运行器只处理完成消息，没有把进度消息持久化。NodeTray 前端只在页面加载时获取一次列表，类型定义和页面均未展示进度，也没有活跃任务轮询。

### 2.5 取消只终止调用方等待，没有终止扫描

本地任务服务已有取消入口和尝试级上下文，但扫描管理器内部仍使用独立后台上下文。取消后，调用方可以返回，枚举、磁盘队列和 Worker 派发却可能继续运行，造成界面状态与真实运行状态不一致。

## 3. 已确认的设计决策

### 3.1 取消全局字节限流器

扫描运行时彻底取消按文件大小加权的全局字节限流。一个文件只占用：

- 所属物理磁盘的一个流槽位；
- Worker 池的一个任务槽位；
- 处理链实际需要的固定大小流缓冲和结果对象。

磁盘间不共享文件字节额度，因此超大文件不会阻塞其他磁盘继续派发任务。

### 3.2 保留盘级流数和 Worker 池作为并发边界

并发继续由以下现有配置和资源边界控制：

- HDD 每盘流数；
- SSD 每盘流数；
- Worker 数量；
- Worker 任务队列容量；
- 数据库批量写入和协议发送批次。

不新增按文件大小、总路径长度或估算内存量的隐式限流器。

### 3.3 兼容旧配置但不再启用字节限流

现有配置中的 `tuning.pending_bytes_mb` 暂时继续允许解析，避免已经发布的 `agent.json` 因未知字段或配置迁移失败而无法启动；该字段不再参与运行时调度，并从新生成的默认配置和相关界面说明中移除或标记为已废弃。

### 3.4 停止任务保留已完成结果并允许重试

停止任务时：

- 已成功提交到本地数据库的文件结果保留；
- 已完成的缓存文件保留；
- 当前任务记录保留并标记为“已取消”；
- 不回滚已经提交的结果；
- 用户之后可以重新创建任务，按现有待处理判定继续扫描或重试失败项。

## 4. 调度与处理链设计

### 4.1 盘级并行

`ScanManager` 为每块识别出的物理磁盘建立独立处理协程组。每组的并发数由磁盘介质类型对应的每盘流数决定。某块磁盘读取大文件时，其他磁盘仍可从自己的队列中取文件并向 Worker 池提交。

删除全局字节限流后，任务流为：

1. 枚举器分批发现文件并写入本地数据库；
2. 待处理文件按物理磁盘分组；
3. 每块磁盘独立按照配置流数读取自己的队列；
4. 每个文件提交到共享 Worker 池；
5. Worker 使用流式哈希或 VideoCore 文件会话完成处理；
6. 结果分批写入 SQLite 并更新任务进度。

### 4.2 统一媒体生产路径

一筛图片与视频统一进入 VideoCore 会话处理路径，复用现有 `processMediaWithDeps` 能力，不重新启用旧版 `mediacore.dll`，也不为发布包增加遗留动态库。

旧版 `mediacore` 代码只保留给显式遗留构建或测试，不得再被默认 Windows Compute 生产路径选中。

### 4.3 缓存目录初始化

Agent 完成配置解析后、启动 Worker 和接收任务前：

1. 解析 `thumb.cache_dir` 的绝对路径；
2. 使用 `MkdirAll` 创建目录；
3. 沿用现有重解析点和路径越界安全校验；
4. 创建或校验失败时阻止相关任务启动并返回明确错误。

不在每个文件处理时重复创建根目录。

### 4.4 前置失败的持久化

若文件在生成 SHA-512 前发生合法终止错误，存储层保存原始阶段、文件标识和错误原因，不再调用要求 64 字节 SHA-512 的编码路径。只有结果声明 SHA-512 已成功生成时才执行长度校验。

这样可以保留首个真实错误，并避免同一文件同时产生误导性的存储错误。

## 5. 进度设计

### 5.1 后端进度来源

Agent 本地任务运行器处理扫描管理器发出的进度消息，并更新本地任务表：

- `stage`：枚举、扫描、后处理或完成阶段；
- `progress_complete`：已经形成终态结果的文件数；
- `progress_total`：当前已知总数；
- `stats_json`：失败数、即时速度、已运行时间以及必要的阶段统计。

进度持久化需要节流，目标为最多每秒写入一次；阶段切换、取消和终态必须立即写入。进度更新失败记录日志，但不得使扫描任务失败。

### 5.2 NodeTray 展示

NodeTray 本地任务页面扩充类型定义并展示：

- 任务状态；
- 当前阶段；
- 进度条；
- `已完成/总数`；
- 失败数和处理速度；
- 活跃任务的“停止任务”按钮。

枚举阶段尚不知道总数时显示不确定进度条；扫描阶段总数大于零时显示确定进度条。页面存在活跃任务时约每秒刷新一次，全部任务进入终态后停止轮询。

刷新页面后，进度从本地任务表恢复，不依赖前端内存状态。

## 6. 停止任务设计

### 6.1 调用链

停止操作采用现有 `local.task.cancel` 语义，补齐以下调用链：

`NodeTray 页面 → NodeTray 应用服务 → Agent 本地任务取消处理器 → 当前任务尝试上下文 → ScanManager`

NodeTray 只发送取消请求，不直接操作 Worker 进程。

### 6.2 扫描上下文传播

扫描管理器接收调用方上下文，不再在任务运行路径创建无法取消的 `context.Background()`。以下位置均检查同一取消信号：

- 枚举回调和枚举批次提交；
- 待处理文件读取与分盘；
- 每盘任务队列投递；
- Worker 池提交前等待；
- 结果收集与终态等待；
- 后续阶段切换。

收到取消后立即停止发现和派发新工作，并释放尚未进入 Worker 的等待项。

### 6.3 已经在 Worker 中执行的任务

停止本地任务不强杀 Worker：

- 已经执行的单个 Worker 任务允许正常完成或由既有超时机制结束；
- 完成结果仍可提交并计入已完成数据；
- Agent 不再给该本地任务派发新文件；
- 任务在所有必要收尾完成后持久化为“已取消”。

前端点击后按钮立即禁用并显示“正在停止”，收到终态后显示“已取消”。重复取消必须幂等。

## 7. 状态与错误语义

本次修改不新增任务状态枚举，沿用现有运行中、完成、失败、取消等状态。状态优先级为：

1. 明确收到取消且任务未完成：`cancelled`；
2. 未取消但处理链发生不可恢复错误：`failed`；
3. 全部阶段完成：`completed`。

单文件失败不会自动把整个扫描任务标记为失败；它计入失败数并保留错误详情。基础设施错误、数据库不可用、缓存根目录无法初始化等任务级错误才使任务失败。

## 8. 兼容性与范围边界

- 不改变数据库中已经提交的媒体分析结果格式。
- 不改变 SHA-512、PDQ、pHash、Sobel 等算法语义。
- 不改变 NodeTray、Agent、Worker 的进程所有权。
- 不把 Worker 直接连接到 SQLite 或 PostgreSQL。
- 不强制删除用户现有 `pending_bytes_mb` 配置。
- 不清理目标发布目录中的数据库、WAL、日志、令牌、配置或现有缓存。
- 本次不解决与该任务无关的 GUI、中央任务或远端 PostgreSQL 流程。

## 9. 测试与验收

### 9.1 自动化测试

至少覆盖：

- 超大文件不再获取全局字节额度，两个磁盘队列可独立推进；
- 取消发生在枚举、队列等待、Worker 提交等待和结果等待阶段时均能结束任务；
- 取消后保留已提交结果，任务状态为 `cancelled`，可重新创建任务；
- 任务进度消息能持久化，更新节流且阶段和终态立即落库；
- NodeTray 活跃任务轮询、进度条、停止按钮、停止中状态和终态展示；
- 一筛图片使用 VideoCore 生产路径；
- SHA-512 前置失败保留原始错误，不生成空 SHA-512 二次错误；
- 缓存目录在启动任务前创建并通过路径安全校验。

### 9.2 构建与静态验证

构建并验证 `worker.exe`、`agent.exe`、`nodetray.exe` 及 NodeTray 前端资源；运行相关 Go、前端和打包测试。检查 Compute 发布清单，确认不新增 `mediacore.dll`，并记录产物 SHA-256。

### 9.3 运行验收

使用至少分别位于磁盘 0 和磁盘 2 的测试目录创建本地任务，验证：

- 两块磁盘可以同时持续产生读取活动；
- 超大文件处理期间另一块磁盘仍持续完成文件；
- Worker 活跃数与盘级流数、文件类型和阶段相符，不再因全局字节额度整体归零；
- 页面在创建任务后出现进度，并在刷新后恢复；
- 点击停止后不再派发新文件，最终显示已取消；
- 已完成结果保留，重新创建任务可以继续；
- 运行日志不再出现旧版 mediacore 不可用、空 SHA-512 二次错误或缓存根目录不存在错误。

磁盘是否“跑满”受源盘性能、文件大小分布、Worker 计算成本和操作系统缓存影响，因此验收以“没有跨磁盘调度阻塞且两盘可持续并行推进”为硬性条件，不承诺所有介质始终保持 100% 活跃时间。

## 10. 发布策略

先在仓库构建区完成自动化测试与运行验证，再生成新的 Compute 发布产物。更新 `D:\code\mySingerServer\publish\MySingerServer-Compute` 时只替换经过清单确认的静态程序和前端资源，保留：

- `data` 目录及 Agent 数据库；
- SQLite WAL/SHM 文件；
- 日志；
- 本地令牌；
- 用户配置；
- 已有缩略图和联系表缓存。

发布完成后记录版本、文件清单、SHA-256 和已执行的验证门禁。GUI、真实磁盘性能、UAC 或长时间运行等未执行验收必须明确标记为 `PARTIAL` 或 `BLOCKED`，不得仅凭构建成功声明通过。
