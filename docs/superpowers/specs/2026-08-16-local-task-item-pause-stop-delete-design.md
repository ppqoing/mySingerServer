# NodeTray 本地任务 Item、实时进度与生命周期控制设计

日期：2026-08-16
状态：设计已确认，等待书面规格复核
适用范围：NodeTray 本地任务页面、本机 Agent、本机 SQLite 任务与分析数据

## 1. 目标

在 NodeTray 创建任务区域下方展示持久化任务 item，并提供可信的阶段、阶段内进度和任务生命周期控制。

本设计交付以下能力：

- 创建成功后立即显示任务 item；
- 持续显示任务状态、业务阶段、阶段内进度、速度、失败数和累计耗时；
- 支持真正暂停、手动继续、安全停止和删除任务；
- Agent 或电脑重启后，暂停任务保持暂停；
- 活动任务删除时自动安全停止，再删除本机任务及其专属分析数据；
- 保留全局文件索引、媒体特征、缓存和文件删除审计；
- 不撤回已经同步到中心端的数据；
- 防止旧页面、旧 API 或迟到控制请求覆盖新任务状态。

## 2. 当前边界

当前本地任务链路为：

`LocalTasksPage → NodeTray Backend → Agent 本地控制协议 → localtask Service → Runner/SQLite`

现有系统已经具备任务创建、列表、取消和重试基础能力，也已保存 `stage`、`progress_completed`、`progress_total` 与统计 JSON。但是当前持久化状态不包含暂停和删除中状态，前端任务展示仍不完整，取消、恢复和任务数据删除也没有形成统一、可恢复的生命周期协议。

本设计扩展现有链路，不新增独立调度服务，不改变 NodeTray 管理 Agent、Agent 管理 Worker 的进程所有权。

## 3. 已确认的产品决策

### 3.1 暂停语义

暂停是真正的安全暂停：停止枚举和新 Worker 作业派发，等待已经进入处理链的单文件或单组工作安全结束，提交其结果后持久化为 `paused`。

恢复沿用同一个任务实例、创建参数和分析运行，从尚无持久结果的文件或候选对继续。断点粒度是文件或候选对，不保存单个大文件内部的字节偏移。

### 3.2 重启语义

Agent 或电脑重启后，`paused` 保持暂停，只有用户明确点击“继续”才恢复。普通意外中断的运行任务仍使用现有自动恢复机制。

### 3.3 删除语义

删除清理：

- 本机任务记录；
- 该任务的本机分析运行；
- 候选对与一筛、二筛、三筛评分；
- 重复组、组成员和本机审核结果；
- 尚未发送的该分析运行 outbox 事件。

删除保留：

- 全局文件索引；
- 图片、视频和帧特征；
- 缩略图与联系表缓存；
- 已执行文件删除操作的批次与明细审计；
- 中心端已经接收的数据。

活动任务点击删除后自动执行“安全停止 → 本机事务删除”。如果被删任务拥有当前本机分析结果，清空当前结果指针，不自动回退到旧结果。

### 3.4 实时刷新语义

NodeTray 使用单一自适应轮询链：存在活动或过渡状态任务时每 1 秒刷新；全部任务稳定或请求失败时每 5 秒刷新。空闲轮询用于发现从其他本机入口创建的任务并从错误中自动恢复。

不在本次范围内引入 WebSocket 或 Wails 事件推送。

### 3.5 阶段与进度语义

UI 使用稳定的业务阶段：等待、枚举与扫描、一筛、二筛、三筛、安全收尾、已完成。

进度条表示当前业务阶段，不计算跨阶段的加权总百分比。总数未知时使用不确定进度条；总数确定后显示当前阶段的完成数与总数。

## 4. 总体架构

现有组件职责保持不变并做最小扩展：

- `LocalTasksPage`：渲染任务 item、轮询快照、提交控制操作和处理前端竞态；
- NodeTray Backend：暴露创建、列表、暂停、继续、停止和删除方法；
- Agent 本地控制协议：验证控制请求并返回安全、结构化结果；
- `localtask Service`：拥有任务状态机、每任务 gate、运行尝试和控制意图；
- Runner：响应带原因的排空请求，停止新工作并等待在途工作；
- Store：持久化状态、阶段、进度、任务实例身份和删除事务。

NodeTray 不直接暂停、停止或强杀 Worker 进程。

## 5. 状态模型

### 5.1 持久化状态

| 状态 | 含义 | 可用操作 |
|---|---|---|
| `pending` | 等待执行 | 暂停、停止、删除 |
| `running` | 正在执行 | 暂停、停止、删除 |
| `waiting_recovery` | 意外中断，等待自动恢复 | 暂停、停止、删除 |
| `pausing` | 已接受暂停，正在安全排空 | 无 |
| `paused` | 已暂停，不会自动恢复 | 继续、停止、删除 |
| `stopping` | 已接受停止，正在安全排空 | 无 |
| `cancelled` | 已停止并保留已完成结果 | 重试、删除 |
| `succeeded` | 已完成 | 删除 |
| `failed` | 任务失败 | 重试、删除 |
| `deleting` | 正在排空或执行本机删除事务 | 无 |
| `delete_failed` | 任务已经停止，但删除事务失败 | 重试删除 |

### 5.2 状态转换

- 暂停：`pending/running/waiting_recovery → pausing → paused`
- 继续：`paused → pending → running`
- 停止：活动状态 `→ stopping → cancelled`
- 暂停后停止：`paused → cancelled`
- 删除：可删除状态 `→ deleting → 记录消失`
- 删除失败：`deleting → delete_failed → deleting`
- 重试执行：`failed/cancelled → pending → running`

控制操作必须先持久化过渡状态，再通知运行尝试排空。旧运行尝试不得覆盖新控制意图或新一轮运行状态。

### 5.3 重启收敛

- `paused` 保持不变；
- `pausing` 收敛为 `paused`；
- `stopping` 收敛为 `cancelled`；
- `deleting` 继续排空或重试本机删除事务；
- `delete_failed` 保持等待用户重试；
- `pending/running` 才进入现有 `waiting_recovery` 自动恢复流程。

## 6. 阶段、检查点与进度模型

`status`、`phase` 和 `stage` 分别承担不同职责：

- `status`：任务生命周期；
- `phase`：面向用户的当前业务阶段；
- `stage`：后端持久化恢复检查点，继续保持内部整数，不直接展示。

`phase` 使用以下稳定值：

- `waiting`
- `scan`
- `stage1`
- `stage2`
- `stage3`
- `finalizing`

任务快照至少包含：

- `taskId`、`instanceId`、`revision`；
- `status`、`phase`、内部 `stage`；
- `progressComplete`、`progressTotal`、`progressTotalKnown`；
- `speed`、`failures`、`duration`；
- 安全错误码和错误摘要；
- 创建时间与最后更新时间。

同一阶段内完成数不得倒退。阶段切换时允许在同一事务中更新阶段并重置阶段内进度。枚举阶段可以持续增加已发现总数，但在枚举完成前 `progressTotalKnown=false`，UI 不把动态总数解释为最终百分比。

进度最多每秒持久化一次；阶段切换、控制意图、排空完成和所有终态立即持久化。单次进度写入失败记录日志并在后续更新重试，不把任务直接标记为失败。

## 7. 暂停、继续与停止数据流

### 7.1 暂停

1. 控制请求在任务 gate 内验证任务实例、revision 和当前状态。
2. Store 将状态写为 `pausing` 并递增 revision。
3. Service 向当前尝试发送 `pause` 排空原因。
4. Runner 停止枚举、新队列投递和新 Worker 提交。
5. 已经进入 Worker 的工作按现有超时规则结束，结果正常落库。
6. Service 保存最新阶段、进度和统计并转为 `paused`。

### 7.2 继续

1. 只接受 `paused` 状态。
2. 使用原任务 envelope、实例身份、阶段检查点和持久化分析运行。
3. 状态转为 `pending`，递增 revision 并建立新运行尝试。
4. Runner 查询尚无持久终态结果的文件或候选对后继续执行。

恢复不会复用单个进程内存队列，也不承诺从文件内部字节偏移继续。没有形成持久结果的单文件或候选对允许重新处理。

### 7.3 停止

停止与暂停使用同一安全排空基础设施，但最终状态为 `cancelled`。已经提交的文件、特征、分析结果和缓存继续保留；未派发工作不再开始。

## 8. 控制接口与并发安全

新增或沿用以下操作：

- `local.task.pause`
- `local.task.resume`
- `local.task.cancel`
- `local.task.delete`

控制接口是异步接受接口：在 gate 内持久化控制意图并通知运行尝试后，立即返回最新任务快照，不等待大文件或整个删除事务完成。NodeTray 通过轮询观察 `pausing/stopping/deleting` 收敛到稳定状态。

每个任务具有：

- 不可复用的 `instanceId`，区分删除后使用同一 `taskId` 创建的新实例；
- 单调递增的 `revision`，标识当前可控制生命周期快照。

`revision` 只在生命周期状态、控制意图或新运行尝试发生变化时递增；常规进度、速度和耗时刷新不递增 revision，避免活动任务的控制请求因每秒进度写入而持续过期。

控制请求携带 `taskId + instanceId + expectedRevision`。后端在任务 gate 内重新读取并校验；不匹配时返回 `stale_task`，不得对新实例或新 revision 执行旧操作。

幂等规则：

- 对同一实例重复暂停，若已是 `pausing/paused`，返回当前快照；
- 重复停止，若已是 `stopping/cancelled`，返回当前快照；
- 删除完成前重复删除返回 `deleting`；删除完成后通过最小删除回执识别同一实例并返回“已经删除”；
- `resume` 只接受 `paused`；
- `retry` 只接受 `failed/cancelled`。

Runner 使用明确排空原因：`pause`、`stop`、`delete`、`process_shutdown`。不得再将所有 `context.Canceled` 统一解释为 `cancelled`。

## 9. 删除事务

### 9.1 前置排空

删除请求先将任务置为 `deleting`。如果存在运行尝试，停止新工作并等待在途工作提交和尝试退出。只有确认该任务不再产生迟到写入后才能进入删除事务。

### 9.2 单事务删除顺序

Store 提供按 `machineId + taskId + instanceId` 删除的方法，并在一个 SQLite 事务中：

1. 定位任务关联的分析运行；没有分析运行时直接进入任务记录清理；
2. 如果它是当前分析，删除 `local_current_analysis` 指针；
3. 将关联 `local_delete_batches.run_id` 置空，保留批次和 `local_delete_items` 明细审计；
4. 删除该运行的 `local_reviews` 本机审核记录；
5. 删除 `local_dup_members` 重复组成员；
6. 删除 `local_dup_groups` 重复组；
7. 删除 `local_pair_scores` 候选对及阶段评分；
8. 删除 `local_outbox` 中尚未发送或等待重试的该运行事件；
9. 删除 `local_analysis_runs` 分析运行；
10. 向 `local_task_deletion_receipts` 写入只包含 `machine_id + task_id + instance_id + deleted_at` 的最小删除回执；
11. 删除 `local_tasks` 任务记录并提交事务。

事务不得删除全局文件、媒体特征、帧特征、缓存、文件删除审计或全局文件/特征同步队列。

最小删除回执只服务于删除幂等和同名新任务隔离，不保存任务目录、envelope、分析内容或错误详情，也不出现在任务列表中。后续使用相同 `taskId` 创建的新任务必须获得新的 `instanceId`；旧删除请求只能命中旧回执，不能操作新任务。

### 9.3 删除失败

数据库忙、锁定等短暂错误使用有限指数退避重试，最大间隔为 30 秒。外键异常、数据损坏或其他永久错误停止自动重试并进入 `delete_failed`，保存安全错误摘要，等待用户点击“重试删除”。

任一步失败都回滚整个事务，不允许产生半删除状态。

## 10. NodeTray 任务 Item

任务列表紧接在创建区域下方，按创建时间倒序显示。创建成功后直接使用创建响应中的任务快照插入或更新列表，再立即刷新一次，不等待下一轮定时轮询。

采用已确认的紧凑单行布局：

`任务模式/创建时间｜状态 · 阶段｜进度条｜完成数/总数｜速度 · 失败数 · 耗时｜操作`

任务 ID 使用次要视觉样式，完整值可通过悬浮提示或详情查看。桌面宽度保持单行；较窄窗口允许受控换行为两行，不产生横向滚动。

操作显示规则：

- `pending/running/waiting_recovery`：暂停、停止、删除；
- `pausing`：正在暂停，按钮禁用；
- `paused`：继续、停止、删除；
- `stopping`：正在停止，按钮禁用；
- `failed/cancelled`：重试、删除；
- `succeeded`：删除；
- `deleting`：正在删除，按钮禁用；
- `delete_failed`：重试删除。

暂停和继续无需确认。停止需要一次简短确认并说明已完成结果会保留。删除确认必须明确说明：

- 将删除本机任务及其分析、分组、评分和审核数据；
- 不删除文件索引、媒体特征和缓存；
- 不删除文件删除操作审计；
- 不撤回中心端数据。

列表刷新失败时保留最后一次可信任务快照，并标记“状态可能已过期”；不得把任务列表清空。

## 11. 前端请求与竞态处理

页面使用单一 `setTimeout` 轮询链，避免多个 interval 重叠：

- 活动或过渡状态：1 秒；
- 稳定状态、业务错误或请求异常：5 秒；
- 组件卸载时取消定时器并废弃未完成请求结果。

每次列表请求和控制操作绑定当前 API generation。任务按钮锁绑定 `api generation + instanceId + revision + operation`。旧 API、旧任务实例或旧 revision 的 Promise 完成后，不能：

- 更新新页面任务列表；
- 写入新任务 item 的状态或错误；
- 释放新一轮操作的按钮锁；
- 触发针对新 API 的额外刷新。

后端返回 `stale_task` 时，前端保留当前 item、解除旧操作锁并立即刷新，不自行猜测最终状态。

## 12. 错误处理

协议返回安全、稳定的错误码，至少区分：

- `task_not_found`
- `task_instance_mismatch`
- `stale_task`
- `invalid_task_state`
- `local_task_unavailable`
- `task_control_failed`
- `task_delete_failed`

单项操作错误显示在对应任务 item 内。列表级错误显示在列表顶部，但保留已有数据。未知内部错误只记录到 Agent 日志，UI 不显示路径、SQL 或堆栈等敏感细节。

如果控制响应丢失但控制意图已经落库，下一次列表轮询必须能够恢复真实状态。

## 13. 数据迁移与兼容性

SQLite 迁移需要：

- 扩展任务状态约束；
- 增加 `phase`、`progress_total_known`、`instance_id` 和 `revision`；
- 增加最小任务删除回执表及 `(machine_id, task_id, instance_id)` 唯一约束；
- 为旧任务生成不可复用的实例身份；
- 将旧任务 phase 从现有 stage 和 status 映射为最接近的业务阶段；
- 保持现有 envelope、任务 ID、已完成进度和统计数据不变。

旧版 NodeTray 不会发送新控制操作；新版 Agent 继续兼容创建、列表、取消和重试的现有请求格式。新控制接口要求实例身份与 revision，不提供不安全的降级控制路径。

## 14. 自动化测试

### 14.1 Store

- 迁移旧数据库并验证新字段、状态约束和默认映射；
- 覆盖所有合法与非法状态转换；
- 同阶段进度单调、阶段切换原子重置；
- revision 乐观并发校验和实例身份校验；
- 删除回执幂等、同名新任务隔离和旧删除请求无害化；
- 删除事务逐表验证、当前指针清理、审计保留和全局数据保留；
- 注入每个删除步骤失败，验证完整回滚和 `delete_failed`。

### 14.2 Service 与 Runner

- 在 pending、枚举、队列等待、Worker 在途处理和一至三筛中暂停；
- 暂停后不再派发新工作，在途工作结果仍落库；
- 恢复只处理未完成文件或候选对；
- 停止、删除和进程关闭使用正确退出原因；
- 重启时各过渡状态按规则收敛；
- 并发暂停、继续、停止、删除和重试由 task gate 串行化；
- 迟到旧尝试不能覆盖新 revision 或删除状态；
- 相关并发测试同时运行普通和 race 模式。

### 14.3 协议与 NodeTray

- 新操作编解码、授权和安全错误映射；
- 创建成功立即出现任务 item；
- 1 秒/5 秒轮询、错误恢复和卸载清理；
- 未知总数与确定总数进度展示；
- 所有状态的按钮矩阵与确认文案；
- 旧 API、旧实例、旧 revision 和迟到 Promise 竞态；
- 前端组件测试、lint 和构建。

## 15. 真实运行验收

在实际 Compute 包中使用足够大的测试目录执行：

1. 创建扫描并自动分析任务，确认 item 立即出现；
2. 观察阶段和阶段内进度持续刷新；
3. 运行中暂停，确认新派发停止且在途工作安全结束；
4. 重启 Agent，确认任务仍为暂停；
5. 点击继续，确认从持久化文件或候选对检查点推进；
6. 验证停止任务保留已完成结果；
7. 验证运行中直接删除会先排空，再移除 item；
8. 查询本机数据库，确认任务专属分析数据已删除；
9. 确认文件索引、媒体特征、缓存和文件删除审计仍保留；
10. 确认中心端已有数据未被撤回。

未执行真实 GUI、Agent 重启、磁盘活动和实际数据库验收时，结论必须标记为 `PARTIAL` 或 `BLOCKED`，不能仅凭静态检查、自动化测试或构建成功宣称完整通过。

## 16. 明确排除范围

- Web GUI、Manager 和中心端任务控制；
- 中心端结果级联删除；
- 强杀或操作系统级暂停 Worker；
- 单文件字节偏移级断点恢复；
- WebSocket 或 Wails 事件推送；
- 批量暂停、批量删除、优先级和新调度队列；
- 删除源媒体、全局索引、媒体特征或缓存；
- 创建后修改任务目录、模式、扩展名或重扫参数；
- 与本地任务 item 无关的 GUI、发布或数据库重构。
