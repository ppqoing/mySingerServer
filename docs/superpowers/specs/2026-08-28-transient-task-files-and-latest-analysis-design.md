# Rust V2 主功能收敛、瞬态任务文件与最近分析结果设计

## 1. 目标

本次调整将计算任务、本地分析和删除运行态从节点 SQLite 中移出，解决基础缓存阶段虽然已经使用批量 `SELECT`，却仍被逐文件任务事务拖慢的问题。

最终数据所有权固定为：

- SQLite 只保存文件、内容、媒体特征、文件故障和中心同步事实。
- 计算任务使用按物理盘拆分的瞬态 UTF-8 TSV 文件，并在内存维护当前运行状态。
- 本地分析只保留最近一次成功结果的 UTF-8 TSV 文件。
- 删除使用当前运行的瞬态 TSV 队列，不保存历史，也不跨重启恢复。
- Node 重启后不恢复计算、分析或删除进度；重新发起任务即可得到正确结果。

任务文件和分析结果禁止使用 JSON，也不生成持久化 `.idx` 文件。

## 2. 方案选择与功能范围

### 2.1 保留的主功能

只保留与媒体去重主流程直接相关的功能块：

- 文件枚举：默认 Everything，不可用时回退 Windows Walker；一个扫描任务可以包含多个根。
- 物理盘识别与调度：枚举前解析物理盘编号和 SSD/HDD/unknown 类型，按配置额度、全局额度、权重轮转和老化保护调度。
- 缓存与计算：SQLite 真正批量只读查询、完整性判断、缺失字段掩码、按盘 TSV 任务、Worker 计算和结果提交。
- 当前运行稳定性：Worker 在同一次运行内崩溃时只让当前项失败并补建 Worker；其他文件和物理盘继续计算。
- 本地长期事实：内容、当前文件位置、媒体特征、联系表、文件故障和同步 outbox/cursor。
- 多机器同步：Node 增量 outbox、PostgreSQL 提交、ACK、游标追赶和必要的整库快照。
- 去重分析：精确重复、相似图片、相似视频、二筛、代表直连分组、本地分析和 Desktop 跨机器分析。
- 结果使用：最近一次本地成功结果、Desktop 自己的跨机器结果、滑动窗口查看、预览、复核和安全删除。
- 性能与运维：Worker/读取线程/磁盘额度等必要配置，当前运行的 CPU、磁盘 I/O、队列、Worker 和失败遥测，构建、打包和真实媒体验收。

### 2.2 删除或简化的后期发散功能

以下功能不再进入产品运行路径：

- SQLite 任务、任务项、阶段的持久化、启动恢复、running 回退 queued、恢复任务 ID 和历史任务列表。
- WorkerPool “prepare → SQLite requeue → restart” 恢复链。手工重启计算引擎时直接取消当前任务、重建 WorkerPool，用户重新发起任务。
- 本地分析运行、阶段、输入、候选、分组、复核的 SQLite 恢复，以及 `retry_phase2` 对旧运行的续算。
- Desktop 跨机器协调器的 `resume`、旧运行自动续接和 `retry_unresolved`。未完成运行在 Node/Desktop 重启或任务消失时结束；重试就是创建一次新的完整分析。
- 删除批次、删除项、墓碑历史、失败项重试和跨重启续删。删除只消费本次瞬态队列。
- 为恢复而新增的统一 `TaskCatalog`、`ScanSessionCatalog` 或第二份任务状态。当前任务只由 `RuntimeTaskRegistry` 管理；Node actor 只保存已完成扫描的根、revision、统计、outbox 高水位和成功清单文件路径，不复制全量对象。
- 独立的数据库表诊断页、文件故障清理页和相应管理协议。连接/schema 校验失败只显示连接状态并写日志；文件故障保留为计算事实和当前任务失败明细。
- 配置保存的双文件事务 journal、替代进程 prepare/commit、CAS 补偿和重连验证链。只保留现有配置路径内的字段校验与单文件原子替换，配置在显式重启 Node 后生效。
- 任何为本方案新增的磁盘满自动清理、历史归档、任务索引文件或兼容旧实现的迁移层。

同一运行内的 Worker 崩溃隔离不是任务恢复，必须保留。outbox 重放、ACK 和快照是同步正确性机制，也必须保留；它们不能被“删除恢复功能”一并移除。

### 2.3 数据方案

采用“保留缓存 SQLite，运行态转为瞬态文件和内存”的方案：

- 保留当前 schema 3，避免现有文件和媒体特征缓存全部失效。
- 旧任务、分析和删除表在启动时清空，后续不再写入。
- 不创建新的任务数据库或临时分析数据库。
- 不删除现有表，等以后确有必要升级不兼容 schema 时再物理移除。

未采用的方案：

- 直接升级 schema 并删除表会迫使现有节点重建全部媒体缓存。
- 使用临时 SQLite 保存运行态仍会产生事务、WAL 和写锁，不符合降低缓存阶段写入的目标。
- JSONL 解析成本和字段分派高于固定列 TSV，不用于任务或分析结果。

## 3. SQLite 数据边界

SQLite 继续保存：

- `metadata`：产品 schema 和文件库 revision。
- `contents`、`files`：内容键、媒体类型、文件路径和当前有效状态。
- `image_stage1`、`image_stage2`、`video_metadata`、`video_frame_stage1`、`video_frame_stage2`：媒体特征缓存。
- `contact_sheets`：联系表相对路径。
- `file_faults`：磁盘读取故障和 Worker 崩溃事实。
- `sync_outbox`、`sync_state`：PostgreSQL 增量同步和已提交游标事实。

SQLite 不再保存：

- 计算任务、任务项、扫描根和任务阶段。
- 本地分析运行、阶段、输入、候选、分组、成员和复核决定。
- 删除批次、删除项和删除墓碑历史。

启动时在一个事务中清空旧运行态表。清理不得删除 `contents`、`files`、特征、故障、联系表或同步数据。

删除成功后仍需更新 `files.active=0` 并写文件状态同步事件。这是当前文件事实，不是删除历史。

同步只传播跨机器去重需要的内容键、当前文件位置及 active 状态、图片/视频特征和删除形成的文件状态变化。任务、任务阶段、运行进度、本地分析结果、复核决定、删除队列、文件故障详情和本地联系表路径不进入 PostgreSQL。连接中断后的 outbox 重放、ACK 和 SnapshotRequired 仍按现有事务边界工作。

## 4. 基础缓存查询

### 4.1 查询阶段只读

枚举完成后形成当前进程内的稳定清单和固定总数。每批最多 1,000 项，直接调用现有 SQLite 批量缓存接口：

```text
机器 ID + 规范路径 + 文件大小
    -> files
    -> contents
    -> 图片/视频特征与联系表
```

查询前禁止：

- 创建任务项。
- 更新任务或阶段。
- 打开逐文件事务。
- 把文件状态改为 queued/running。

批量查询的 SQL 数量必须与批次大小无关。正常 1,000 项路径批次继续使用固定数量的业务 `SELECT`。

### 4.2 完整性分类

查询结果不是简单的命中布尔值，而是每个文件的有效字段和缺失字段掩码。

以下情况视为缺失：

- `NULL`、空字段或数据库约束之外的长度。
- 非法或零尺寸的媒体元数据。
- `base_complete=false`。
- 缺少规定的视频槽位或槽位字段。
- 显式计算失败状态或历史失败占位符。
- 缺失、损坏或与内容键不匹配的联系表。

合法的全零特征不能仅凭数值判断为默认占位符。纯色图像可能产生合法零值，完整性必须由显式状态、字段长度和结构规则共同判断。

后续不再把 Worker 失败写成特征占位符。失败只写 `file_faults`，对应字段保持缺失，使下一次新任务可以重试。

缺失字段使用稳定数值掩码表达，至少覆盖：

- MD5。
- 媒体探测和媒体元数据。
- 图片一筛、图片二筛。
- 视频元数据。
- 视频一筛槽位 0～5。
- 视频二筛槽位 0～5。
- 联系表。

完整缓存命中项不生成任务记录。部分命中项只计算掩码指定的字段，不重复计算已有有效字段。

## 5. 按物理盘拆分的任务文件

### 5.1 文件布局

每次计算创建独立运行目录：

```text
data/node/runtime/<run-id>/
  PhysicalDisk7-hdd.tasks.tsv
  PhysicalDisk8-ssd.tasks.tsv
  PhysicalDisk5+12-unknown.tasks.tsv
  scan-success.tsv

data/node/runtime/delete-<run-id>/
  delete.tasks.tsv
```

任务文件统一位于 Node 数据目录，不写入媒体根。文件名中的物理盘身份只表达任务归属。

路径在枚举边界已经绑定物理盘编号和类型。缓存查询后，只有需要计算的项才写入对应物理盘任务文件。

### 5.2 固定行格式

任务文件使用 UTF-8、无 BOM、制表符分隔和固定列顺序。每行只表示一个需要计算的文件：

```text
状态\t任务项ID\t工作类型\t规范路径\t显示路径\t文件大小\t已知MD5\t缺失字段掩码
```

- `P`：待计算或正在计算。
- `C`：所需结果已经成功提交 SQLite。
- `F`：本轮文件计算失败。

状态是每行第一个固定单字节。任务文件管理器在追加时记录行偏移，SQLite 提交成功后只把 `P` 原位修改为 `C`；文件级失败修改为 `F`，不重写整行。

Windows 文件名不能包含制表符或换行，路径字段无需 JSON 转义。所有非路径枚举、ID、整数、MD5 和掩码均使用固定 ASCII 表达。

### 5.3 文件是实际调度来源

任务文件不是日志副本，而是当前运行的调度来源：

1. 缓存查询生产者按批向各物理盘文件追加任务并刷新可见边界。
2. 每个物理盘读取器顺序读取自己文件的下一批 `P` 项，只保留有限预读窗口。
3. 统一磁盘调度器根据配置中的 SSD/HDD/unknown 每盘额度和全局额度选择 lane。
4. 全局额度不足时按配置权重轮转，并保留老化保护，避免低权重 HDD 饥饿。
5. 缓存生产者完成后封闭所有任务文件；所有记录进入 `C/F` 后本轮计算终止。

同一个 `TransientTaskFileSet` 独占文件句柄、追加游标、读取游标和状态偏移，其他组件只通过明确命令访问，避免并发 seek/write 破坏行边界。

`scan-success.tsv` 与计算任务文件不同：它按规范路径排序保存本轮完整缓存命中项和本轮结果已提交成功项，文件级 `F` 不进入。它是当前进程分析输入的准确清单，不是恢复文件或历史；不生成 `.idx`，Node 启动时随 runtime 目录删除。

成功清单每行固定为：

```text
S\t规范路径\t显示路径\t文件大小\tMD5\t媒体类型
```

尾记录保存行数和前面字节的 SHA-256。

## 6. Worker 与 SQLite 提交

调度给 Worker 的身份包含 run ID、任务项 ID、物理盘身份、任务文件行偏移和缺失字段掩码。Node 必须核对同一身份后才能接受结果。

执行顺序固定为：

1. Worker 只计算掩码要求的字段。
2. Node 校验媒体类型、固定长度、有限浮点值、视频槽位和内容键。
3. NodeStore 在事务中合并新增结果，不用缺失或失败值覆盖已有有效缓存。
4. 必要时写入或更新 `contents`、特征表、`files`、`file_faults` 和同步 outbox。
5. SQLite 事务提交成功并返回 ACK 后，任务文件状态才从 `P` 改为 `C`。
6. Worker 或单文件读取失败时状态改为 `F`，其他物理盘继续调度。

Node、Worker 或 SQLite 在 ACK 前退出时，任务行最多保持 `P`。运行目录会在下次启动清空并由新缓存查询重新生成，因此不会把未提交结果误判为完成。

## 7. 扫描收尾与正确性

缓存命中项虽然不写任务文件，但仍加入当前进程内的本轮已见路径集合。只有以下条件同时满足才能收尾：

- 全部缓存批次查询完成。
- 所有物理盘任务文件已经封闭。
- 所有任务行进入 `C/F`。
- 所有 SQLite 结果 ACK 已返回。

收尾前先写完并封闭 `scan-success.tsv`，保存行数和 SHA-256；失败则不收尾。随后收尾事务批量写入新增或变化的文件关系，并按扫描根和路径组件失效本轮未出现的旧活动位置，同时写同步 outbox。只有 SQLite 事务提交后，Node actor 才注册该成功清单。

枚举失败、任务取消、任务级基础设施错误或进程退出不得调用收尾事务，因此不会错误失效旧文件。单文件 `F` 计入本轮失败，但不阻塞其他文件和任务终态。

成功收尾时递增 SQLite `metadata` 中的文件库 revision。该 revision 只表示分析输入可见的文件集合发生变化，不因普通运行时进度更新而变化。

## 8. 运行任务与协议

`RuntimeTaskRegistry` 是当前进程任务、阶段、进度、Worker 和最近失败的唯一事实源。任务中心和总览页不得从 TSV 或旧 SQLite 任务表重建第二份状态。

任务中心、总览最近任务和 running count 必须从同一份 Registry 快照一次更新。普通 `ViewChanged`、PostgreSQL 连接状态或其他页面刷新不得写任务字段，避免界面在 `base_compute`、空列表和旧快照之间反复切换。

Registry 直接使用业务 Task ID，并保存任务类型、当前状态、统计、阶段、Worker 摘要、最近失败和完成时 outbox 高水位；不再为持久任务建立 Runtime ID 映射，也不新增 `TaskCatalog`。Node actor 只额外保存 `TaskId -> CompletedScanSnapshot` 小映射，其中只有扫描根、revision、统计、outbox 高水位、成功清单路径及其 SHA-256。

Task ID、Analysis ID 和删除批次 ID 仍通过现有协议暴露，但只在当前 Node 进程有效：

- 当前进程内已完成计算任务仍可被本地分析选择。
- 任务完成时的 outbox 高水位保存在内存任务快照。
- Node 重启后旧 ID 返回任务不存在，Desktop 清除对应运行状态。
- 重启不自动重建或继续旧任务，用户重新发起扫描、分析或删除。

Node 启动先删除 `data/node/runtime`、未完成分析 `.partial.tsv` 和旧 SQLite 运行态行，再发布空任务列表。Desktop 每次连接或刷新都用 Node 返回的完整列表替换该节点任务模型；空列表必须清除旧显示，不能把断线前任务伪装成仍在运行。

成功扫描快照在当前进程内保持不变。普通同步只读取这些结果，不会让快照过期；只有后续成功扫描收尾或成功删除改变文件库 revision 后，旧快照不能再用于开始新的分析。多个根需要作为同一个扫描任务提交，避免人为组合不同 revision 的清单。

`data/node/runtime` 在启动时按精确目录边界清空。清理不得扩大到 Node 数据目录、缓存目录、媒体根或生产目录。

## 9. 最近一次本地分析结果

### 9.1 生命周期

本地分析运行状态、冻结输入、候选、分组和复核决定只存在当前进程内存及当前 `.partial.tsv`：

```text
data/node/results/latest-analysis.partial.tsv
data/node/results/latest-analysis.result.tsv
```

- 启动时删除 `.partial.tsv`。
- 分析失败或取消时删除 `.partial.tsv`。
- 新分析运行期间继续保留并允许查看上一份成功结果。
- 新分析成功后原子替换 `.result.tsv`。
- 任意时刻只保留最近一次成功结果。

### 9.2 结果格式

结果使用版本化 UTF-8 TSV。头记录包含格式版本、分析 ID、文件库 revision、分析模式、阈值和创建时间。每个最终组成员占一行，并重复保存查看所需的组信息，避免读取时再做关联查询：

```text
记录类型\t分组类型\t分组ID\t是否代表\t代表MD5\t代表大小\t机器ID\t规范路径\t显示路径\tMD5\t文件大小\t一筛分数\tpHash通过块数\t二筛分数
```

尾记录保存数据行数和前面字节的 SHA-256。完成发布顺序为：

1. 写完数据和尾记录。
2. 刷新并关闭文件句柄。
3. 使用 Windows 原子替换语义替换旧 `.result.tsv`。
4. 替换成功后才向 UI 发布新结果。

发布前失败不得影响旧成功结果。

### 9.3 滑动窗口读取

结果查看不使用分页和持久索引：

- UI 只持有当前可见行及前后预读窗口。
- 后台顺序扫描 TSV，校验格式、行数和 SHA-256，但不把全部结果对象加载进内存。
- 已经扫描到的行偏移只保存在当前进程内存。
- 向后滚动超过窗口时使用内存偏移重新读取。
- 跳到尚未扫描的位置时，后台继续顺序扫描到目标位置并显示加载状态。
- 重启后首次打开重新扫描，不生成 `.idx`。

结果头的文件库 revision 与当前 SQLite revision 不一致时，结果仍可只读查看，但必须明确标记“数据已变化”，并禁止从该结果直接执行删除。

### 9.4 本地与跨机器分析边界

Node 本地分析只接受当前进程已完成且 revision 仍匹配的扫描快照，校验并读取其成功清单，再按清单内容连接 SQLite 当前文件事实并冻结输入；完成后发布最近一次本地 TSV，未完成分析不恢复。Desktop 跨机器分析只消费已同步到 PostgreSQL 的内容、位置和特征，自行保存自己的完成结果，不读取也不依赖 Node 的本地分析结果。

Desktop 或 Node 重启、所选 Task ID 消失、节点离线超出当前运行门禁时，当前跨机器分析结束并清空未完成状态。界面不提供“继续旧分析”；用户再次操作会从当前同步事实创建新的完整分析。

## 10. 删除边界

删除计划由内存生成后写入当前运行的固定 TSV 队列：

```text
状态\t删除项ID\t模式\t机器ID\t规范路径\t显示路径\t文件大小\tMD5
```

- `P`：尚未处理。
- `C`：文件已回收或永久删除，且 SQLite 当前文件事实已经提交。
- `F`：本项验证或文件系统操作失败；继续处理下一行。

删除执行器顺序读取该文件，每次只处理一行。文件是本次删除的实际队列，不是历史日志；不生成 `.idx`，不分页，不恢复。任务终态后删除队列文件和运行目录；Node 启动时直接删除遗留队列。

创建删除计划时必须验证分析结果 revision 仍是当前 revision，并在内存冻结本批次。随后每个文件执行前必须重新验证：

- `LocationKey` 当前活动。
- 实际文件大小仍匹配。
- 流式 MD5 仍匹配结果中的内容键。

删除成功后先在 SQLite 事务中更新 `files.active=0`、递增文件库 revision 并写文件状态同步 outbox，提交 ACK 后才把行改为 `C`。删除失败改为 `F`，只更新当前内存详情和普通进程日志。

任一成功删除都会递增 revision，并使当前分析结果变为过期。revision 变化不撤销已经冻结的同一删除队列，该队列仍按逐文件路径、大小和 MD5 校验继续处理；新的删除计划必须等待重新分析。进程退出后遗留队列在启动时删除，用户重新扫描和分析。

## 11. 错误处理

- 缓存批量查询失败时不生成该批任务行，也不返回部分分类结果。
- 任务文件批量追加或刷新失败属于任务级基础设施错误，停止本轮且不执行扫描收尾。
- 非法任务行、重复任务项身份或行偏移不匹配立即停止本轮，不能调度猜测数据。
- SQLite ACK 失败时任务行保持 `P`，不能提前标记 `C`。
- Worker 返回未请求字段时拒绝该项，不能覆盖缓存。
- 分析结果格式、行数或校验值错误时拒绝展示并要求重新分析。
- 运行目录清理只允许作用于已解析的 `data/node/runtime` 和精确 `.partial.tsv`。
- 磁盘空间不足时当前写入和当前任务明确失败；本方案不自动删除缓存、构建产物、日志或媒体文件。

## 12. TDD 与验收

实现必须使用真实行为测试，不使用读取源码文本判断是否修改。

### 12.1 SQLite 和缓存分类

- 1,000 条缓存查询通过 SQL trace 证明只有固定批量 `SELECT`，查询前无任务 `INSERT/UPDATE`。
- 完整图片、完整视频、普通文件、部分字段、空字段、非法尺寸、失败占位和缺槽视频分别得到准确缺失掩码。
- 合法全零特征保持命中。
- Worker 部分结果只补缺失字段，不覆盖已有有效字段。

### 12.2 任务文件与调度

- 缓存完整命中不生成任务行。
- 部分命中只写请求掩码。
- 两个物理盘生成两个独立任务文件。
- 成功清单同时包含完整缓存命中和 SQLite ACK 成功项，不包含 F；格式、行数和 SHA-256 可校验。
- 调度器真实从任务文件顺序读取，并保持配置权重、全局额度和老化保护。
- SQLite 提交失败时状态保持 `P`；成功 ACK 后改为 `C`；文件失败改为 `F`。
- Worker 崩溃只结束对应行，其他磁盘继续运行。
- 重启清空运行目录并重新查询缓存生成任务。

### 12.3 分析和删除

- 启动清除 `.partial.tsv`，保留 `.result.tsv`。
- 新分析失败或取消不覆盖旧成功结果。
- 新分析成功只保留最近一次结果，并通过原子替换和校验。
- 滑动窗口不会把全部结果对象载入内存，也不创建 `.idx`。
- revision 不匹配时结果只读且删除入口禁用。
- 删除从固定 TSV 顺序执行，不写删除表；成功 ACK 后行变为 `C`，失败行变为 `F` 并继续，结束后队列删除。

### 12.4 范围收敛

- Node 重启后 RuntimeTaskRegistry 和完成扫描映射为空，SQLite 长期缓存仍可命中。
- Worker 当前运行内崩溃会补建，但计算引擎重启不 requeue 旧任务。
- Node 本地分析和 Desktop 跨机器分析均不能恢复未完成运行；重试创建新运行。
- Desktop 跨机器分析只读取 PostgreSQL 同步事实，不读取 Node 本地分析结果。
- 产品协议和 UI 不再暴露恢复任务、继续旧分析、重试旧删除、数据库表诊断或文件故障清理入口。
- outbox 重放、ACK、游标和 SnapshotRequired 行为保持正确。

### 12.5 回归和真实媒体

- node-store、node-engine、protocol、desktop-core 和 desktop-ui 相关行为测试全部通过。
- `cargo fmt --all -- --check` 与 `git diff --check` 通过。
- 使用真实媒体执行完整扫描，记录缓存查询吞吐、任务文件生成、Worker CPU、各物理盘 I/O 和最终结果。
- 再次运行相同媒体时，完整缓存命中项不得进入任务文件。
- 测试通过前不打包、不替换 `I:\Tool`。

## 13. 完成标准

满足以下条件才算完成：

1. 基础缓存查询阶段不再创建或更新 SQLite 任务记录。
2. 只有真正缺少计算数据的文件进入对应物理盘任务文件。
3. Worker 只计算缺失字段，SQLite ACK 后任务行才标记完成。
4. 任务文件成为实际调度来源，并保持当前按物理盘加权与老化保护语义。
5. Node 重启清空全部运行态，不恢复旧计算、分析或删除任务。
6. SQLite 只保留长期缓存、故障和同步事实。
7. 本地分析只保留最近一次成功 TSV，失败结果不能覆盖它。
8. UI 使用滑动窗口动态加载，不分页、不使用 JSON、不生成 `.idx`。
9. 删除只使用本次瞬态 TSV 队列，不保存历史、不恢复，仍通过重新验证、SQLite ACK 和 outbox 保证当前结果正确。
10. 未完成的 Node 本地分析和 Desktop 跨机器分析均不能跨重启继续；Desktop 不依赖 Node 本地分析结果。
11. 非核心恢复、诊断和重试入口已经从产品代码、协议与 UI 删除；同步一致性和当前运行内 Worker 崩溃隔离保持。
12. 实现完成并通过行为测试后，最后更新 `AGENTS.md`，只记录已经落地的最终结构和验证命令。
13. 行为测试、回归测试和真实媒体验收均无新增失败。
